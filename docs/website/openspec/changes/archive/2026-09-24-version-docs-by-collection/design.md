## Context

The site is a statically exported Next.js app on Fumadocs 16. A single `defineDocs` in `source.config.ts` covers `content/docs`, and `src/lib/source.ts` loads it with `loader({ baseUrl: '/' })`. One catch-all route, `src/app/(docs)/[[...slug]]/page.tsx`, renders every page, and every derived surface — sitemap, `llms.txt`, `llms-full.txt`, the per-page Markdown manifest, the OG images — enumerates from that one loader.

Five properties of the current implementation shape this design.

- **Search is Inkeep, not the built-in index.** `provider.tsx` mounts `@/components/inkeep-search` as `RootProvider`'s `SearchDialog`, and the navbar's toggles are the Ask AI ones. Fumadocs' own search is still wired at `src/app/api/search/route.ts` through `createFromSource(source).staticGET`, and `src/components/search-dialog.tsx` still exists, but nothing mounts the dialog — the index is kept against a future need, not served to a reader. So version-scoping retrieval means Inkeep attributes, and the static index is a build cost with no reader attached.
- **Navigation is hand-authored.** `src/lib/custom-tree.ts` exports a `Node[]` with one `root: true` folder per collection, and the layout passes the collection bar explicitly as `sidebar={{ tabs: collectionTabs }}`. There are no `meta.json` files, so folder structure drives URLs but not the sidebar. The collections change chose this deliberately, while recording that the calculus changes once collections are versioned independently. The loader nonetheless builds `source.pageTree` on every build; the site simply ignores it.
- **Versioning already exists, in miniature, and in the shape this change generalizes.** `src/lib/versions.ts`, generated by `scripts/update-versions-list.ts`, describes two versioned sections: the SDK API reference and the release notes. Each serves its latest series from `index.mdx` at the version-less path and its history from `v0.15.x.mdx` siblings — latest unversioned, archives versioned. `VersionSelector` in `page-actions.tsx` already switches between them from the page actions strip, with entries, labels, and destination URLs precomputed at build time by `getVersionSelectorProps()` so the client bundle carries no version index.
- **Every URL is served with a trailing slash, except that dotted segments opt themselves out.** Sevalla's Pretty URLs normalizes a slash-less path to its trailing-slash form, so that is the form readers are served — but it skips a path whose final segment contains a dot, reading it as a file request, and it does not resolve such a directory to `index.html` either. `public/_redirects` therefore supplies both halves by hand for the archived slugs: a `200` rewrite from `/…/:version/` to that directory's `index.html`, then a `301` from the slash-less form to the trailing-slash one. The order is load-bearing — Sevalla's placeholder matcher is lenient about the trailing slash, so putting the `301` first makes it match the with-slash request and redirect to itself, an infinite loop that was verified empirically. `computeSectionVersionUrl` emits the trailing-slash form for the same reason. Every non-current line URL this change introduces inherits all of it.
- **Redirects are CDN configuration, not application code.** `public/_redirects` is consumed by Sevalla and its last rule is a catch-all `/* /404.html 404`, so anything generated must be inserted above it. `scripts/check-redirects.ts` replays a captured URL set against the built output.

The gates that constrain the work are `tests/sidebar-consistency.test.ts`, `tests/link-integrity.test.ts`, the `@vahor/next-broken-links` step inside `build`, and `scripts/check-redirects.ts`.

## Goals / Non-Goals

**Goals:**

- Make the documentation line — one `MAJOR.MINOR` folder — the unit of versioning, for the SDK and the Provider, without versioning the site.
- Introduce versioning without changing a single URL the site publishes today.
- Isolate each line's corpus for humans and for agents, so no surface mixes two lines.
- Keep the build a static export with no server-side runtime.
- Absorb the existing patch-series versioning rather than leaving two versioning schemes in the same collection.
**Non-Goals:**

- Support statuses beyond current-and-older, and per-line compatibility manifests pinning exact package releases. Both are deferred; the manifest declares which lines are published, and nothing more about them.
- Engineering URL continuity past what a redirect rule expresses. `public/_redirects` is the whole mechanism; no route, module, or function is added to keep an old URL alive, and a mapping no rule can express is a URL that 404s and is recorded as such. Versioning happens to cost nothing here — the version-less paths keep resolving on their own — so the rules are only for the archives and for pages a cut drops.
- Deciding what becomes of the oldest line when a cut would exceed two. The build refuses that cut rather than guessing, and this change specifies no removal procedure: with both Provider lines released, nothing here has to be undone later.
- Automating content production. Cutting a line, copying a README out of a tag, rewriting link text in a file: all done by hand here. The build's job is to reject the result when it is wrong, not to produce it.
- The App and Research collections.
- Materializing lines from git branches or tags, and keeping the door open for it. Duplicated folders are not an implementation detail behind an interface; they are how a line exists, and code reads them directly. The earlier direction carried a requirement that a later storage change must leave every public surface untouched, which nothing in this change could exercise — its only scenario fires when the storage is replaced — while pulling the implementation toward an indirection layer with no present reader. Replacing the storage later is a change with its own design, and it will find the contract where the contract actually lives: the URL rules, the manifest, and the artifacts.
- A custom version-aware MCP layer. Managed MCP stays a soft scope, measured rather than guaranteed.

## Decisions

### The current line is a Fumadocs folder group, so its URLs do not move

`content/docs/sdk/(v0.19)/js-ts-sdk.mdx` resolves at `/sdk/js-ts-sdk/`, because Fumadocs excludes a parenthesized folder from the slugs of its children. `content/docs/sdk/v0.18/js-ts-sdk.mdx` resolves at `/sdk/v0.18/js-ts-sdk/`. Both facts come from the framework's page conventions, and the restriction that matters — groups work on directory names only, never file names — costs nothing here, since a line is always a directory.

This is what makes the change non-breaking. The alternative, giving every line a version segment and redirecting the unversioned paths to the current line, would move roughly seventy URLs, make every canonical URL churn on each release, and turn every external link to the docs into a redirect hop. It also mirrors what the reference and release notes already do, so the site keeps one story about where the latest content lives instead of two.

The cost is that "which line is current" is expressed by a rename. A rename is a reviewable diff that cannot disagree with the content it renames, and the manifest records the folder name rather than a separate flag, so the two never state it twice.

### Cut the next line as soon as a release is live

The cut happens the day after a release, not on the day of the next one: rename `(v0.18)` to `v0.18`, keeping exactly what the site is serving, and copy it to `(v0.19)`, which then receives the coming release's edits. `main` therefore carries an unreleased version as its current line for most of the cycle, and that is the objective rather than a side effect.

It is what keeps the editorial flow to one rule: the folder that receives edits is always the folder group, and it is always the version shipping next. Nothing is written in one place to be moved to another later, no page is reclassified at release time, and an author never has to know where in the cycle they are. The release cadence is what makes this safe — the whole monorepo ships fortnightly, every package together, the docs with them — so "the version being prepared" is unambiguous, and there is never a moment when two future versions compete for the group.

Readers are unaffected because the site deploys as part of a release. Prod's folder group is therefore the version that was just released, even though `main`'s has been the next one since the previous cycle. The cost is that a deploy outside a release would publish the unreleased line as current, which the cadence makes a non-event but which is the one assumption to keep in view.

A cut is made for each package with a version scheduled in the coming cycle, so a collection whose tracked package has nothing scheduled simply keeps the lines it has.

A cut fixes where a line's content comes from, not whether it may change afterwards. `v0.18` is an ordinary folder of MDX: its pages can be corrected, and pages can be added to it, at any time and with no ceremony. The only rule is directional — material describing the new release belongs in the current line, not backported into an older one.

Two things fall out of this that the earlier direction did not have. The older line is accurate by construction — it starts as what was live, not as documentation written ahead of a release and hoped to be right. And a cut retires no URL: the version-less paths keep resolving and simply move to the new release, which is what they already do today on every release, so the only redirects a cut needs are for pages the new line drops — all of them to the current line's index, one destination rather than a per-page mapping, since a cut that drops pages has not happened yet and the shape of that mapping is better decided against a real one.

It also decouples the collections. The SDK carries `(v0.19)` because `0.19` is the `@qvac/sdk` version being prepared, while `@qvac/cli` has `0.13.1` out and nothing scheduled, so its current line is the release that is live rather than the one coming.

The Provider still publishes two lines, and both are real: `@qvac/cli` has shipped every minor back to `0.2`, so `(v0.13)` is the current release and `v0.12` the one before it. This matters more than it looks. The alternative considered was cutting `(v0.10)` ahead of any release purely to demonstrate switching on a second collection, which would have put a version not on npm behind the Provider's version-less paths, and would have needed a withdrawal procedure — and a specification for it — to undo the fiction later. Taking the previous release instead exercises the same machinery with nothing invented: two lines, a switcher, versioned URLs, per-line artifacts and retrieval scoping.

What is invented is smaller and admitted: `v0.12` starts as a copy of what the site serves today, because documentation for `0.12` was never written separately. The line is an ordinary content folder, so anything materially wrong for `0.12` can be corrected there — which is exactly the affordance an older line is supposed to have, now exercised for real rather than hypothetically.

### Declare the line set in one hand-edited manifest, and check it against the folders

`src/lib/versions.ts` becomes the manifest of every piece of software this site documents at more than one version: for each, the package it is, where it is documented, and the lines published, each line recording its version and the folder holding it. Everything version-shaped reads it — the switcher, canonical URLs, `versions.json`, per-page metadata, retrieval filters — instead of scanning directories.

The file is already this, in miniature and for two sections: its own header calls it a version manifest, and `API_SECTION` and `RELEASE_NOTES_SECTION` are exactly the shape being generalized. Two things change. The unit becomes a collection's line rather than a section's patch series, and the file stops being generated: `scripts/update-versions-list.ts` retires with the archives it maintained, so a human edits the constants. That is the point rather than a concession. Adding a version is then two hand edits in one reviewable diff — the folder and the entry — and no tool stands between the operator and either half.

Constants in TypeScript rather than a JSON or YAML data file, because the same reasons that made the current file TypeScript still hold: the compiler is the schema, so a malformed entry fails the typecheck instead of needing a validator and a dependency; every consumer imports it directly, which is what a static export wants; and it is the convention the repository already reads.

A line records two facts, its version and its folder, and no third one. Whether it is current is visible in the folder it names, since the current line's folder is written `(v0.19)` and the others `v0.18` — so currency is never stated twice and cannot be stated inconsistently.

The manifest declares and the folders realize, which only works if the build refuses to let them disagree. The structure check becomes a bijection: every declared line has the folder it names, every line folder under a versioned collection is declared, and exactly one of them is a group. A folder cannot publish itself by being created, a declaration cannot point at nothing, and a cut that renames the folder without touching the manifest fails rather than serving an older line as current.

What the manifest deliberately does not carry yet is what was deferred for good: support statuses, per-line compatibility with exact package releases, and the ability to declare a folder present but unpublished — which the bijection forbids outright, and which is the one capability worth revisiting first if drafting a line in the open ever becomes necessary.

### Keep one Fumadocs collection, one loader, and no route segment for the version

`source.config.ts` keeps its single `defineDocs`, `src/lib/source.ts` keeps one `loader({ baseUrl: '/' })`, and the catch-all `[[...slug]]` keeps serving every page with `generateStaticParams` returning `source.generateParams()`. The line is already inside the slug, or deliberately absent from it.

One loader per collection or per line was rejected for the reason the collections design anticipated: the loader maps files to URLs, the folder already does that correctly, and splitting it multiplies the enumeration points every derived surface reads from. A `[collection]/[version]/[[...slug]]` route was rejected because in a static export where all params are enumerated at build time, a route segment buys no dynamic behaviour.

### Make the line switcher the collection control, configured over lines

The switcher is `SidebarTabsDropdown`, the component Fumadocs already renders for `sidebar.tabs`, given the lines instead of the collections and placed in the sidebar's `banner` slot. It is exported from `fumadocs-ui/components/sidebar/tabs` alongside `isTabActive` and the `SidebarTab` type, whose optional `urls` set is precisely how a line declares which pathnames belong to it. So the switcher's implementation becomes the construction of that option list, and nothing else.

Everything that would otherwise have been written comes with it. The dropdown is already a client component: it reads `usePathname()` from `fumadocs-core/framework`, resolves the active entry through `isTabActive`, and renders each option as a `Link` from `fumadocs-core/link` — a router navigation the framework prefetches, not a document load. That is the no-reload, no-flicker requirement satisfied by the component's own default rather than by a rule this change has to enforce, and it disposes of the current widget's `window.location.href`, whose comment blames a soft-navigation limitation the static export does not actually have: the export emits per-segment RSC payloads as `__next.*.txt`, which every sidebar link already uses.

`VersionSelector` is therefore not reused but removed, and the retirement of the patch-series archives is what makes that free: switching between `vX.Y.x` siblings was its only job. `src/lib/versions.ts` goes with it — `API_SECTION`, `RELEASE_NOTES_SECTION`, `computeSectionVersionUrl`, `getVersionSelectorProps` — and `archivedVersionsTree` with them. The line index that replaces all of it is smaller than what it deletes, and there is one switching mechanism on the site instead of two.

The slot lands the control in the right place on every viewport without conditional layout code. The notebook layout renders `banner` as the last child of the sidebar header, after `nav.children` and after the collection `SidebarTabsDropdown`, which `tabMode="navbar"` hides at `lg` and up since the navbar carries the bar there. A narrow viewport gets collection, then line, then tree; a wide one gets the bar in the navbar and the line switcher alone above the tree. Both read outward-in, and the two controls being the same component is what makes the pairing legible rather than accidental.

Labelling is the one thing the option list has to supply: `v0.19 (latest)` for the current line and plain `v0.18` for the others, the form the archived series already used. The suffix is derived from which folder is the group, not stored, so it follows a cut without an edit.

The unresolved part is whether a payload fetch under a dotted version segment survives the CDN rules that dotted paths already need. The version-less current line is unaffected, so switching back to it always soft-navigates; the question is only entering an older line, and the spike answers it before any of this is built.

The switcher belongs to the tree, not to the page. Everything below it — every sidebar entry — changes when the line changes, while the page actions strip is about the page in front of the reader: copy it, open it as Markdown, ask about it. Placing the switcher there would put a control that replaces the entire navigation context inside a group of controls that act on one page.

Since the switcher no longer sits next to the content, the page still has to state its own line: the requirement that a versioned page declares its applicability in the rendered text covers that, and it survives copy-paste in a way a chrome badge does not.

### Let each line declare its own navigation, and splice it into the hand-authored tree

`custom-tree.ts` stays the place collections are declared. Platform and Resources stay entirely hand-written. A versioned collection contributes one `root: true` folder per line, and each of those folders takes its `children` from the subtree the loader already built for that line's directory out of `meta.json` files placed inside it.

What forces this is that lines have to be able to differ. A release adds a page, drops one, renames a section, reorders a group; that is what versioning documentation means. Declaring a collection's navigation once and resolving it against each line — the earlier direction here — quietly forbids all of it, and the gate meant to catch drift would then fire on legitimate divergence instead. Putting the navigation inside the line's own folder makes divergence the default and costs nothing to maintain, because the copy that cuts a line carries the navigation with it.

Four framework facts make it work, all verified against the installed version rather than assumed. `getSlugs` skips any path segment matching `/^\(.+\)$/`, so the group contributes no slug and a versioned sibling contributes its own — the URL a line's pages get is already right, which is why no prefixing step survives this decision. The page-tree builder emits a node per directory keyed as `` `${rootId}:${folderPath}` ``, so a line's subtree is addressable by path rather than by position. `loader()` builds that tree whether or not anything consumes it, so reading it adds no loader, no collection, and no build step. And the collection bar is passed explicitly, so a collection holding two root folders still contributes exactly one tab.

The costs are real and worth naming. The repository ends up with two navigation dialects — TypeScript for unversioned collections, `meta.json` for versioned ones — which is defensible only under the reading that versioned content carries its own navigation, and that is the reading taken here. Converting the SDK and Provider subtrees is roughly 290 lines of TypeScript becoming a `meta.json` per directory, expressing the same ordering, separators, titles and icons. `loader({ icon })` resolves lucide names only, so the two `@icons-pack/react-simple-icons` entries the SDK tree uses must be added to that resolver for a `meta.json` to name them.

The alternative kept longest was a hand-written declaration per line in `custom-tree.ts`. It permits divergence just as well and changes no convention, but the cut becomes two manual moves instead of one, with nothing tying the second to the first: copying the folder and forgetting the declaration yields a line whose sidebar silently belongs to its sibling. It also hand-copies 270 lines per cut into a file that grows with every line.

`tests/sidebar-consistency.test.ts` now walks a tree that is part declared and part derived. For the declared part its job is unchanged. For the derived part an entry can only dangle when a `meta.json` names a file that is not there, which is exactly the mistake worth catching, and the divergence between lines it used to treat as an error is no longer one.

### Resolve content links per line at build, and keep authoring them version-less

The sidebar of an older line resolves to that line because the loader built it there, but the links inside the prose are a different matter, and that is where the folder group presents its bill. Content today holds 288 internal links, of which 287 are absolute and version-less — `/sdk/configuration/`, `/platform/architecture/` — and one is relative. Nothing prefixes them: Fumadocs emits an author's link as written. In the current line that is already right, because the group contributes no segment. In `v0.18` it is wrong in the worst way: the link resolves, to the current line, so a reader following it leaves the version they were reading with nothing to notice.

Rewriting the links when a line is cut is the obvious fix and the wrong one. The codemod exists — `scripts/rewrite-internal-links.ts` did exactly this for the collections move — so the cut itself is cheap. The cost is permanent and lands elsewhere: the two folders stop being copies, so every subsequent comparison between lines is dominated by prefix noise, every page corrected in an older line must be written in a form nobody uses in the current one, and a single forgotten prefix reintroduces the silent jump. Authoring links relative instead — `../../configuration/` — is genuinely line-agnostic, since the line prefix sits above the deepest `..` and `trailingSlash: true` fixes the arithmetic. Fumadocs neither helps nor hinders: it ships no relative-link resolver, so the href reaches the browser as written and the browser resolves it correctly. What kills the idea is that both safety nets are absolute-only. `link-validator.ts` extracts on `href="(\/…)"` and `](\/…)`, and `@vahor/next-broken-links` skips any href that does not start with `/` when no `--domain` is passed. Going relative would quietly drop all 288 links out of validation, which is a steep price for a property the build can provide instead — on top of 288 edits, a link form that breaks whenever a page changes depth, and prose the author can no longer read as a destination.

So the resolution happens at build, from the one fact that is never ambiguous: the file's own path tells the build which line the page belongs to. A remark plugin prefixes same-collection absolute links on pages of an older line and leaves everything else alone. The choice of remark over rehype is what makes this correct rather than merely convenient — `includeProcessedMarkdown: true` means the Markdown twin is emitted from the processed markdown, so a rewrite at the mdast level reaches the HTML and the `.md` from one pass, while a rehype pass would fix the page and hand agents links pointing out of their line.

The plugin itself is not worth a dependency. It visits `link` nodes and rewrites `url`, which `unist-util-visit` — already installed — reduces to about fifteen lines. Packages like `remark-link-rewrite` exist and would trade those lines for an async replacer API and a version to track. The same fifteen lines, differently configured, are what pin the inventory's README links to their tag, so the repository ends up with one small plugin shape used twice rather than two dependencies.

The rewrite deliberately stops at the collection boundary, which is the same rule the artifact gate enforces: a link to an unversioned page has no line to be prefixed with, and a link to another versioned collection resolves at that collection's current line, since nothing pins the SDK's `v0.18` to a Provider line. Authors keep writing one form everywhere, and no line is ever the exception.

`link-integrity.test.ts` walks the MDX source rather than the build output, so it has to learn the same resolution — a version-less link on a `v0.18` page must be checked against `v0.18`'s folder. That turns the existing check into the isolation gate for free: a page that exists only in the current line, linked from an older one, fails there and nowhere else. The build-time broken-link step needs nothing, since it reads resolved URLs. The repository has served content from a `(latest)` group before, and that test's comment still records the adaptation, so the combination is not new ground.

### Reduce the patch-series archives to the current series

Each line's folder holds its own reference and release-notes pages, so the sibling-file scheme has nothing left to do. The sixteen `v*.mdx` files move to `content/_unpublished/` and their URLs redirect to the current series. `scripts/create-version-bundle.ts`, which froze `index.mdx` into a `vX.Y.x.mdx` sibling, is retired with the `release-version-*` orchestrators that drive it.

Nothing indexed is lost: the archived API pages are already `noindex` with a canonical pointing at the latest, and every release's notes exist in `CHANGELOG_LLM.md` and GitHub Releases. The content is retained in the repository rather than deleted, because the Software Inventory is where per-package reference and release history belongs, and it is authored two phases later in this same change.

### Publish agent artifacts from routes enumerated over the line set

`llms.txt` and `llms-full.txt` gain a collection level and a line level as sibling route handlers whose `generateStaticParams` enumerates the resolved lines; the root files stay where they are and become routers.

The two levels compete for one URL, and the resolver wins it. `/sdk/llms.txt` cannot be both the resolver and the current line's page index, so the index of every line — the current one included — is published under its version, at `/sdk/v0.19/llms.txt`. Nothing else lives under that prefix while the line is current, but the artifact is the one thing an agent addresses by version rather than by currency: it reads `0.17.2` out of a lockfile and substitutes, with no round trip to learn which line the version-less paths happen to serve. The corpora keep the page rule instead — the current line's at `/sdk/llms-full.txt`, another line's at `/sdk/v0.18/llms-full.txt` — because a corpus is the content itself, and each line's index names its own corpus, so nothing is guessed either way.

The page actions popover loses its "View full docs dump" entry, which hardcodes `/llms-full.txt`. Keeping it would mean resolving the reader's line to pick a corpus and explaining to a human what a corpus is — a page-level affordance worth designing on its own, not as a side effect of versioning. Removing it also removes a way to hand a reader on one line the wrong line's corpus, and leaves `llms.txt` as the single entry point, which is what an agent follows anyway. `versions.json` is generated the same way. Every generator filters pages by line, and a build gate asserts that no line-scoped artifact references another line — the property most likely to break silently as content is copied between lines.

That gate also has to resolve the artifacts' URLs, which looks redundant next to `@vahor/next-broken-links` and is not. The step globs `**/*.html`, the sitemaps and `page.js`, and pulls links out of `<a href>` and `<img src>`; it never opens a `.txt`, and the file set it validates against is built from those same globs plus `public/`, so the artifacts are invisible to it both as sources and as targets. The per-page Markdown is outside it for the same reason. Nothing needs to be crawled twice, though: the gate is already reading each artifact line by line to classify URLs, so resolving them against the built page set in that pass costs a lookup, and the corpora are generated from the page list anyway — the URLs that can actually rot are the handwritten ones in the root router and the protocol page.

### Scope retrieval with Inkeep attribute filters, and publish the line explicitly

Inkeep supports what this needs. Filters are declared as `filters.attributes` on `InkeepBaseSettings`, or per surface on `InkeepSearchSettings` and `InkeepChatSettings`, using MongoDB-style operators (`$and`, `$or`, `$in`, `$nin`, `$eq`, `$exists`), evaluated against attributes attached to ingested content. The documented example is this exact case — scoping a query to a version and an SDK — and the filter can be computed per page, which is how the reader's line reaches the request.

Two findings change the plan. First, Inkeep infers `product` and `productVersion` from HTML or URL structure by default, and the current line's URLs deliberately carry no version, so inference would mislabel it; the line must be published as an explicit page attribute and the filter must read that attribute rather than a URL-derived one. Attributes are ingested from `inkeep:`-prefixed meta tags in the page head, which is where the build writes the collection, the tracked package, the line, and whether the line is current.

Second, the AI Assistant does not go through the UI component: `use-ask-ai-chat.tsx` calls the OpenAI-compatible chat completions endpoint directly. That path does carry attribute filters, which the spec had left open. Inkeep's own chat hook, in `@inkeep/cxkit-primitives`, calls the same endpoint through the same OpenAI SDK and sends `JSON.stringify({ ...baseFilters, ...chatFilters })` as an `inkeep-filters` request header — the full filter object, `attributes` included, not source IDs alone. So the assistant is scoped exactly as the widget is, by adding one header beside the ALTCHA solution it already sends. Search keeps the declarative path: the modal passes `searchSettings.filters`, and the widget puts it in the GraphQL query variables.

One deliberate departure from the requirement as written. A query from inside a line reaches that line, the unversioned collections, **and the current line of every other versioned collection** — not just the first two. It is the rule a line's pages and artifacts already follow: the collections are cut independently, so nothing pins one release of the SDK to one release of the Provider, and the stricter reading would mean a reader in the SDK searching for the HTTP server finds nothing. The property the lines exist for is unaffected: no other line of the reader's own collection is ever retrieved.

### Start the inventory as the packages' READMEs, taken from their tags

The inventory's first version publishes one page per line: `packages/<pkg>/README.md` as it stood at that release, in full. Four packages — `@qvac/sdk`, the Python client, `@qvac/cli`, `@qvac/ai-sdk-provider` — hold 1,385 lines of README between them, written by the people who ship the packages and reviewed at each release. Authoring usage pages and wiring per-line generated references would produce, at best, a worse version of text that already exists, and it carried a dependency nobody wanted: a previous line's API reference means running TypeDoc at an old tag, which is tooling this change has no business building. The README plan removes that, and what it publishes is accurate by construction.

The inventory addresses its packages differently from the product collections, and deliberately. A package's version-less path serves an index — published name, one sentence, repository and registry links, and the list of documented versions — while every README, the newest included, lives at a versioned path. No folder group appears in the inventory at all.

The two shapes cannot coexist anyway: an `index.md` in the package folder and an `index.md` in a folder group inside it both claim the package's path, and Fumadocs does not reject that. The spike measured what happens — the group's index is served and the other file is dropped, published at no URL at all, with no warning — so the choice is forced, and worth making on the merits.

What differs is what the reader is doing. A product collection is read in flow, so "the newest" is the right default and the version is a mode you are in. An inventory entry is a catalogue record with one page per release, consulted by enumeration — which versions exist, what did `0.13` say — and hiding the enumeration behind a switcher weakens the one thing the inventory is for. The agent case is sharper: the corpus protocol has an agent read the version installed in a project, and for a package that is an exact number out of a lockfile. With versions explicit in every URL and an index listing them, resolution is a lookup; with the newest at a version-less path, the agent must know that convention and then check the manifest to learn whether the newest is the one it wants. It also removes a latent contradiction — the artifact and retrieval specs say a Platform page publishes no documentation line, which would have left the newest README of a package at a URL carrying neither a version segment nor a line attribute.

So the inventory publishes package *versions*, not documentation lines: same folder naming, no group, and every version addressed by its own segment. Where the reader moves between them was decided twice; the last paragraph of this section records the second answer.

The list on that index is hand-written, like everything else here, so it can rot. The cheap defence is a check rather than a generator: the manifest already declares each package's versions, so the correspondence gate also asserts that an index links exactly those. The one real cost is that every inventory content URL now carries a dotted segment and therefore depends on the `200`/`301` rules — which the `:version` placeholders already express per depth, not per page.

The packages are declared in the same manifest as the collections, with the same two facts per version — the number and the folder. Which tag a page was taken from stays on the page, where the reader sees it, rather than being restated in the manifest.

The versions come from the tags, so the inventory's numbering is each package's own: `sdk-v0.19.1` and `sdk-v0.18.2`, `ai-sdk-provider-v0.7.0` and `ai-sdk-provider-v0.6.2`, `cli-v0.13.1` and `cli-v0.12.0` — the CLI's tags run back to `cli-v0.2.0`, so its previous minor is `v0.12`, taken at its last patch. Where a package also anchors a collection the two numberings coincide, which is the anchor working rather than a shared scheme: `@qvac/ai-sdk-provider` anchors nothing and numbers itself `v0.7`. The Python client is the one that cannot be read off a tag, and needs no tag of its own: its `pyproject.toml` declares `dynamic = ["version"]` stamped from `packages/sdk/package.json`, so it ships under the SDK's number and takes its versions from the SDK's tags. All four therefore publish two versions, and the site has no single-version case to reason about.

Every one of those tags exists, so every version page is read from one. An earlier draft of this change documented lines that had not shipped, and allowed the newest README to come from `main` when its tag had not been cut yet; the release train has since passed those versions, and the exception is gone with it.

Taking the text from the tag, rather than including the file from the working tree, is what makes both lines possible. Fumadocs can include a file live, but the working tree is `main` — it is not the current release, and the previous release's README is not in it at all. `git show <tag>:packages/<pkg>/README.md` prints what to paste, once per line, and the page records the tag so its provenance survives in the content rather than in a script's memory. Eight pastes are cheaper than the tool that would avoid them, and a tool that keeps pages in sync with tags is a different feature — one worth building after the pages exist and their shape has stopped moving.

One thing has to be done to the text on the way in. Its repository-relative links — `../bare-sdk/README.md`, `./e2e/README.md`, `./docs/serve-openai.md`, `./examples/notebook.ipynb` — mean nothing to a reader on the site, so they become GitHub URLs pinned at the line's tag, which keeps an older line pointing at what it actually described; the site already links `github.com/tetherto/qvac/tree/main/...` from content, so the destination is not a new idea.

Three things the pages settled once written. The Markdown processor keeps raw HTML's text and drops its tags, so the SDK banner's four links arrived as dead words — it goes, as the badge row it is, along with the CLI's table of contents, which the site renders itself; every placeholder the READMEs carry in prose sits inside code, and survives. The tag a page came from is stated in the page's first line rather than in frontmatter, because frontmatter here is a validated schema that renders nothing: a field naming the tag would be dropped on parse and read by nobody, while the line is what a reader — and the Markdown twin an agent fetches — actually gets. And the broken-link step's exemption widened from one path segment to any, since an inventory version sits three deep; it exempts the same thing it always did, a dotted segment Next strips the slash from, which `scripts/check-redirects.ts` then proves resolves in both forms.

Seen in a browser, the plan of moving between versions from the index alone was wrong, and in a way the reasoning above could not have caught: it argued about where the enumeration should live and never asked what the sidebar does with a version page. Two faults, one cause. The versions were listed in the sidebar under their package, which made the inventory the one place on the site where a version is a navigation entry rather than a property of the reading — a second grammar for the same idea the switcher already expresses. And opening one produced the wrong sidebar entirely: Fumadocs scopes a sidebar to the last root folder on the path it finds by matching the pathname against the tree, page URL against page URL, normalizing the pathname's trailing slash but not the node's. Those entries were written with the slash a dotted segment needs at the CDN, so they matched nothing, and the reader who opened a README was shown the list of collections. The slash was never needed there: Next rewrites every href it renders to the form the route takes, adding the slash or, for a dotted final segment, leaving it off, so what the node carries decides only whether the page can be found.

Both are answered by giving the inventory the same control the collections use. The switcher lists a package's versions with its index among them — `All versions`, `v0.19`, `v0.18` — and the sidebar goes back to one entry per package, so the version is a property of the reading here as everywhere else, and the index keeps the enumeration, with its release links and its dates, for the reader who wants the catalogue rather than a jump. The version pages then have to be named in the tree, or they match nothing again: each is named as the index of a root of its own, holding the Platform navigation, since a root's index is not itself an entry. That is the mechanism the collections already use — a root per line — applied one level down, and it costs a manifest-derived list, not a special case. The structure gate now asserts what the browser found: every inventory page resolves to a root, in both slash forms, and no version appears among a root's children.

What does not have to be done is adapting the files to MDX, and that is worth stating because the obvious plan is to sanitize them. The SDK's README opens with a raw HTML banner — `<br>`, `<sup>`, `<a href=...>` inside a blockquote — whose unclosed tags JSX rejects, and the Python README carries a `<version>` placeholder in prose. Writing a sanitizer for that is unnecessary: `defineDocs` already accepts both extensions, its default is `doc: ["mdx", "md"]`, and the processor is chosen per file by extension, so a page written as `.md` is parsed as Markdown with JSX and expressions off. The hazards stop being hazards. What the Markdown processor does with the banner's raw HTML — render it or drop it — is the one thing the task has to observe, and dropping a row of badges costs the documentation nothing.

## Risks / Trade-offs

- **Folder groups may interact badly with the artifact routes and the broken-link step** → Groups are a documented Fumadocs convention, but this site combines them with a catch-all route, a static export, and `@vahor/next-broken-links`. Spiking one line pair end to end — a group page, a versioned page, and a line-scoped artifact route — retired this risk before any content moved; see Spike Findings.
- **Dotted segments still need hand-written rules, now for older lines only** → `v0.18` is read as a file request by Pretty URLs, so neither the trailing-slash normalization nor the directory index happens for it on its own. The existing treatment applies unchanged, including the `200`-before-`301` ordering, and `computeSectionVersionUrl` already emits the safe form; the risk is a new call site that forgets it. The redirect check must cover every older-line URL in both forms. Implementing it turned the slash-less rule from a courtesy for inbound links into a load-bearing one: Next reads a dotted segment as a file as well, and strips the trailing slash off a line index whatever the page tree hands it, so the site's own sidebar links that form. `@vahor/next-broken-links` resolves only the trailing-slash form, so it is told to ignore line indexes and `scripts/check-redirects.ts` is what proves they resolve.
- **Client-side navigation into a dotted version segment may not survive the CDN** → A soft navigation fetches `__next.*.txt` payloads under the destination path, and dotted paths are exactly where Pretty URLs behaves differently. If those fetches fail, the router falls back to a hard navigation and the switch flickers — the behaviour the spec forbids. The spike found those payloads exported inside the dotted directory with dotted names of their own, so they resolve as plain file hits and the transport is sound. The browser half is still unwatched, so the switcher task confirms one navigation by hand.
- **Artifact routes may collide with the docs catch-all** → `/sdk/v0.18/llms.txt` competes with `[[...slug]]`. Next.js prefers the more specific route, and the spike confirmed it in the export: a dynamic line-scoped route built alongside the full catch-all page set.
- **The assistant may not be scopeable on its current request path** → Its endpoint documents only source-ID filtering. If attribute filters are unavailable there, the honest outcome is an unscoped assistant plus a stated limitation, not a filter that silently does nothing.
- **Doubling the page count doubles the build** → Every page gains a second copy, and each generates HTML, Markdown, an OG image, and an entry in the unmounted Orama index. The OG route was indeed the bottleneck, and what it cost was memory rather than time: the deployment builder was killed during static generation, having reported no progress past `0/242`, while the same commit built locally in 45 seconds. Reproduced in a container, the phase peaks near 11 GB, because Next runs one worker per core — sixteen there — and each holds Satori and a WASM rasterizer whose footprint grows as it renders. Time was never the problem: 242 pages take under nine seconds. So the build pins `experimental.cpus` to 2, which puts the phase at 6.6 GB, below the ~8.2 GB compilation already costs. The ceiling is now set by a phase that does not grow with the number of lines, and a cut adds seconds rather than gigabytes.
- **A fix that applies to both lines has to be made twice** → Duplicated folders mean a typo or a wrong code sample present in both lines is two edits. Nothing stops the second edit — an older line is editable like any other — but nothing prompts it either, so the reader on `v0.18` keeps the bug when it is forgotten. Accept it at two lines and revisit if the count grows; a cross-line diff report is the cheap mitigation if it starts biting.
- **Two versioning schemes coexist during the migration** → Between retiring `create-version-bundle.ts` and landing the line folders, the release tooling can no longer bundle a patch series and there is nothing yet to cut. Retire it in the same change that moves the content, so neither scheme is half-live.
- **A manual cut is a cut that can be done wrong** → Renaming, copying and editing redirects by hand invites a forgotten step, and the fortnightly cadence means it is done often enough to matter. Every way it can go wrong must be a build failure — the structure check, the redirect replay, the sidebar and link checks, and the leakage gate — so the procedure is validated even though it is not automated. Performing one cut by hand end to end, and writing down the steps, is what a later automation change will start from.
- **The change only archives when every phase is done** → Covering four phases in one change means the spec baseline stays empty until the last one lands. Sequence the tasks so each phase is independently shippable, and if a later phase is deferred, narrow the change with `openspec-update-change` rather than leaving it open indefinitely.

## Spike Findings

The spike built one line pair end to end — a folder-group page, a dot-bearing line with its own `meta.json`, a line-scoped artifact route, and the CDN rules for both — then deleted the content. What it measured:

- **The folder group is excluded from the slug.** A page at `content/docs/sdk/(v0.19)/spike-group.mdx` exported to `out/sdk/spike-group/index.html`, and no parenthesized directory appears anywhere in `out/`. The version-less URL scheme holds.
- **The dotted segment survives the whole pipeline.** `content/docs/sdk/v0.18/**` exported its index and its nested pages, `generate-llm-md-files.ts` wrote the Markdown twins for both the line index (`out/sdk/v0.18.md`) and the pages under it, and `@vahor/next-broken-links` reported zero broken links.
- **A line needs exactly two redirect rules, and only for its own index.** The index is the only URL whose last segment carries a dot, so it alone misses Pretty URLs' slash normalization and directory resolution; every page below it ends in an undotted segment and resolves unaided. Replaying both forms through the CDN model in `check-redirects.ts` resolved each without a loop.
- **The literal segment is preferred, but not because the placeholder breaks.** A `/sdk/:version` placeholder also left the Markdown twins intact, since a built file resolves before a non-forced rule. It is avoided because it claims every first-level SDK path to cover two, and because a literal block makes a cut visible in the diff.
- **The artifact route does not collide with the catch-all.** A dynamic `[collection]/[line]/llms.txt` route exported `/sdk/v0.18/llms.txt` alongside the full `[[...slug]]` page set. Lines do not need a literal folder each.
- **Soft navigation's payloads are reachable.** The RSC payloads sit inside the dotted directory (`out/sdk/v0.18/__next._tree.txt` and siblings). Their own last segment carries a dot, so they are plain file hits that resolve before any rule — the transport a soft navigation needs. What remains unproven is the browser half: no browser automation exists in this repo, so "the router does not fall back to a document load" is confirmed at the transport level only, and the switcher task should watch one navigation by hand.
- **A line folder is a page-tree node addressable by its path.** Both lines appeared as folder nodes — `$id=root:sdk/(v0.19)` and `$id=root:sdk/v0.18`, the latter carrying `index=/sdk/v0.18` — titled from their `meta.json`, with children in the order that file declares (the spike listed its pages against alphabetical order to prove it) and separators honoured. The splice helper can address a line as `root:<collection>/<folder>`.
- **The second collection cost no shared code.** Cutting the Provider — the measurement the SDK could not make, since the infrastructure was written while cutting it — touched only data and content: the manifest gained the two lines, `custom-tree.ts` *lost* the hand-written `providerChildren`, `_redirects` gained the two literal rules any line index needs, and everything else was moving files and writing two `meta.json`. No module learned a Provider case. URL resolution, the switcher, the link rewriting, the artifact routes, and the retrieval attributes all followed from the manifest entry alone, and the single-line state worked before the second line existed. The one thing the move forced into the content was frontmatter: the icons and short sidebar names that lived in the hand-written tree became `icon` and `sidebarTitle` on the pages, which is where a line-declared navigation keeps them.
- **A leftover collection index is silently shadowed.** With both `content/docs/sdk/index.mdx` and `(v0.19)/index.mdx` present, the build succeeded, the group's index was served at `/sdk`, and the other page was published nowhere — while the tree kept the leftover file's title. The cut must *move* the collection index into the group; leaving it behind is not an error the build reports, which is one more reason the manifest correspondence check has to be the thing that catches a half-done cut.

## Migration Plan

1. Spike one line pair: a folder-group page, a versioned page, a line-scoped artifact route, built and served through the CDN rules. Resolve the routing risks before anything else.
2. Land the line-resolution helpers with no content moved, unused by routing until the tree can materialize.
3. Move the SDK content into `v0.18` and copy it to `(v0.19)`, then verify that every URL published today still resolves at its version-less path.
4. Convert the SDK subtree into `meta.json` files inside its lines, and splice one root folder per line into `custom-tree.ts`.
5. Retire the patch-series archives, hand-write the line redirect rules, and replay the captured URL set.
6. Add the line-scoped agent artifacts and their leakage gate.
7. Wire the retrieval metadata and filters, verifying the assistant's request path first.
8. Repeat the content and tree steps for the Provider, which should require no new infrastructure. If it does, that is the signal the helpers were built SDK-shaped.
9. Paste the Software Inventory pages from the four packages' release tags, then rehearse one cut by hand and record the procedure.

Rollback is a branch revert at any step. Nothing migrates data, and `_redirects` is inert once the paths it targets are gone.

## Open Questions

- Whether the retired release-notes archives should be republished under the Software Inventory in this change or left in `content/_unpublished` until a later one.
- Whether a package index should eventually carry more than the minimum it starts with — a name, a sentence, the links, the version list — or whether the READMEs it points at are the whole story.
- Whether a README that changes after its release tag — a typo fixed on `main` — should be allowed to update the published line, or whether the tag is the whole truth.
